Log anomaly detection · HDFS_v1 · 11,175,629 lines · chronological evaluation

A 2009 PCA baseline still beats a DeepLog-style LSTM once the test set comes from the future.

Sessions are split by time: train on the first 60%, choose every threshold on the next 10%, test on the last 30%. Under that rule, principal component analysis on event counts flags anomalous HDFS blocks with an F1 of 0.964. The best LSTM reaches 0.870: it actually catches more anomalies (95.7% against 93.2%), but raises 902 false alarms to PCA's 7.

Does a random split flatter the models?

Only the sequence models. The count models barely notice, because HDFS repeats itself: 99.0% of chronological test sessions replay an event sequence already seen in training (97.7% under a random split).

A time-ordered test set is also the end of the log

The test period is the last 5 hours of a 38.7-hour log, and HDFS blocks are often deleted hours after they are written. So 40% of test sessions end before their delete events, and the read traffic of the early hours has stopped. Every model is judged on these cut-off sessions; a normal session that was merely cut off looks just like one that stopped early.

03

What does each model miss?

Each square is one of the 3,723 anomalous test sessions. PCA judges how often events happen; DeepLog judges what comes next, and the two miss almost completely different anomalies. Adding an END event lets the LSTM see sessions that stop early, and then it catches nearly everything PCA does.

What PCA's 7 false alarms contain

  1. <IP> Served block <BLK> to <IP>>100xin 100% of these sessions vs 0.0% of normal test sessions
  2. BLOCK* NameSystem.delete: <BLK> is added to invalidSet of <IP>1.7xin 100% of these sessions vs 59.4% of normal test sessions
  3. Deleting block <BLK> file <PATH>1.7xin 100% of these sessions vs 59.7% of normal test sessions

Ranked by how much more often a template appears in these sessions than in normal test sessions. PCA's few false alarms all carry read traffic ("Served block"), which almost vanished from the test period. The LSTM's false alarms lean on replication events. Both models' misses are replication sessions too: the replication templates appear in every missed anomaly against 17% of all anomalies. One anomaly in five simply stops early, which is why the LSTM needs the END event at all.

A live system never knows a session has ended; it can only assume so after a stretch of silence. Normal HDFS blocks routinely go quiet for hours before they are deleted, so that stretch has to be 12.3 h (the 99th percentile of the longest pause inside normal training sessions). Count models, and the LSTM whenever it fires on the END event, can only alert after that wait. Published DeepLog fires on the event itself: median 6 s against 12.5 h for PCA.

05

How much training data, and how clean?

Less than you would think, but PCA gets fragile. With 1% of the training period (3,450 sessions, about what DeepLog was trained on), PCA's F1 ranges from 0.724 to 0.964 depending on which sessions it happens to see; LightGBM barely moves, and the LSTM scores 0.902.

Why the parser threshold matters

At Drain3's default similarity threshold (0.4), "PacketResponder N for block X terminating" (1.7M normal lines) and "... Interrupted" (49 failure lines) became one template, hiding a failure signal inside the most common event. Grouping accuracy was 83.4%; at the validation-chosen 0.9 it is 99.78% on test.

Does it hold on another system?

Not on BGL, 4.7M lines from a Blue Gene/L supercomputer over 215 days, and the reason is time rather than any model. The failures change: 42% of test-period alert lines belong to categories that never occur in training. Under a time-ordered split, a one-line rule (flag any FATAL or FAILURE line) beats every model.

BGL has no natural sessions, so the log is cut into 1-hour windows or 20-line windows; a window is anomalous if any line in it carries an alert tag. Each scheme has its own split and its own parser, fitted only on its training period. LSTM rows are 3-seed means. On 20-line windows the rule scores 0.622; every model falls below it once the test data comes from later months.

The same supervised model on the same 20-line windows. Shuffling the windows lets it train on the failures it will be tested on; fitting the parser on the whole log also hands it the test period's vocabulary. Together they turn 0.114 into 0.993, the kind of number published BGL results report.

    About

    LogLens tests whether log anomaly detectors keep their published scores when evaluated on later data than they were trained on. It is a research benchmark on public 2008 data, not a production detector.

    Source code on GitHub

    Data

    • LogHub: the HDFS_v1 log (11.2M lines), block labels, ground-truth templates and event traces
    • LogHub on Zenodo: the archive the pipeline downloads and checksums
    • Drain3: the template miner fitted on the training period
